> This page surfaces the maintained [docker-run reference](https://github.com/getopenpost/openpost/blob/main/docs/reference/installation/docker-run.md) inside the self-hosting guide. The reference stays the source of truth for the command.

Use `docker run` for a quick look at OpenPost, not for an instance you keep. Anything persistent belongs on the [Compose setup](/self-hosting): the run command below keeps data on a named volume but leaves you to retype every flag on each restart, with no file to back up or version.

## Try it

The published image supports `linux/amd64` only; the explicit `--platform` flag keeps other hosts from silently pulling the wrong expectation. See the [reference](https://github.com/getopenpost/openpost/blob/main/docs/reference/installation/docker-run.md) for the full command and `.env` guidance.

```sh
docker volume create openpost_data
docker run -d --platform linux/amd64 --name openpost --restart unless-stopped \
  -p 8080:8080 --mount source=openpost_data,target=/data --env-file .env \
  -e OPENPOST_DATABASE_PATH=/data/db/openpost.db \
  -e OPENPOST_MEDIA_PATH=/data/media \
  -e OPENPOST_MEDIA_URL=http://localhost:8080/media \
  ghcr.io/getopenpost/openpost:latest
```

Then open `http://localhost:8080`, create the first account, and check `http://localhost:8080/api/v1/ready` for `"status":"ready"` and `"database":"ok"`.

## Make it permanent

When the trial convinces you, move to [Self-host OpenPost](/self-hosting) and copy your `.env` secrets over so saved provider credentials stay readable. Set the three public URLs to the real HTTPS origin before connecting social accounts; `localhost` URLs never survive that move. Then work through [provider integrations](/self-hosting/integrations) and [backups](/self-hosting/maintenance) before relying on the instance for scheduled posts.
